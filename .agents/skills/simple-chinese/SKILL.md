# 简明中文

本仓库的中文文本写给一个赶时间、只读一遍的读者。每句话读一遍就要读懂。

规则的结构参考 ASD-STE100 简化技术英语：一句一事、限长、一个东西一个名字、条件在前。英语语法层面的规则（冠词、时态、情态动词）不适用于中文，已去掉。

## 适用范围

| 用 | 不用 |
|---|---|
| `README.md`、给机主的报告和提问、会话之间的派活和交活消息、memory 笔记 | `AGENTS.md`、`docs/`、代码注释和提交信息。这些用英文写，按 [`enforce-rules-for-ai-tone`](../enforce-rules-for-ai-tone/SKILL.md) |

## 步骤

1. 确认读者。想了解这个移植的人读 README，机主读报告和提问，接活的会话读派活消息。
2. 把每段分成「操作」或「说明」。操作告诉读者做什么，说明告诉读者是什么。两种不混在一段里。
3. 动笔前先定词。一个概念只选一个词，全文不换（见规则 1.1 与「定词」）。
4. 按下面的规则写。
5. 交付前跑「自检」。这一步必做。
6. 不改「不动的内容」里列出的东西。

审查别人的文本时，每处问题按这个格式报：规则编号、原文、改写。只引用本文件里存在的编号。

## 规则

### 1 词

| 编号 | 规则 |
|---|---|
| 1.1 | 一个东西一个名字。全文用同一个词指同一个东西，不为了避免重复换说法。 |
| 1.2 | 硬件和系统组件用它们自己的名字：主线 Linux 的驱动名和寄存器名、iPadOS 的进程名和服务名。不自己起别名。 |
| 1.3 | 术语第一次出现写全称，后面可以用简称。 |
| 1.4 | 不用口语。白搭、翻车、炸了、病根、路子、直接敲，写成不生效、事故、崩溃、根因、途径、执行。 |
| 1.5 | 不用空话词，见「空话替换表」。删掉后意思不变的词就删掉。 |
| 1.6 | 能数出来的写数字，不写「大量」「若干」「一系列」。能由脚本算出来的数字不手写进文档，手写的数字会过时。 |
| 1.7 | 动作用动词表达。写「校验镜像」，不写「对镜像进行校验」。 |

### 2 句子

| 编号 | 规则 |
|---|---|
| 2.1 | 一句只说一件事。 |
| 2.2 | 操作句不超过 30 字，说明句不超过 40 字。计数方法见本节末尾。 |
| 2.3 | 条件放在动作前面。写「如果日志环是空的，先读 ramoops」，不写「先读 ramoops，如果日志环是空的」。 |
| 2.4 | 说清谁做了什么。写「内核跳过这个分区」，不写「该分区会被跳过」。 |
| 2.5 | 不用分号。分号两边写成两句。 |
| 2.6 | 不省成电报体。主语、宾语和「的」该有就有。 |
| 2.7 | 三件以上并列的事用列表，不挤在一句里。 |

计数方法：每个汉字与中文标点算 1。一段连续的英文、数字、代码、路径或标识符整体算 1。所以 `tools/xnu_screen.py --system-suspend-test 180` 只算 1，长路径不会把句子撑爆。

### 3 段落与结构

| 编号 | 规则 |
|---|---|
| 3.1 | 一段一个主题，最多 5 句。 |
| 3.2 | 先写结论，再写依据。 |
| 3.3 | 标题写陈述句。写「eMMC 上的五个分区」，不写「为什么要分五个区」。 |
| 3.4 | 需要横向对比时用表格。同类条目并进一张表，不拆成多张单行表。 |
| 3.5 | 只写现在是什么、怎么用、动了会坏什么。不写这段文字以前长什么样。 |
| 3.6 | 源码阅读、主机检查和上机结果分开写。编过、测试通过、写盘读回一致，都不是上机结果。 |

### 4 公开文本

`README.md` 公开可见，而且永久可搜。报告和派活消息不公开，但 4.1、4.4、4.5 同样适用。

| 编号 | 规则 |
|---|---|
| 4.1 | 只写事，不写人。不写谁提的、谁拍板、私下怎么沟通的。理由落在技术依据上。 |
| 4.2 | 不写本地环境：本机路径、`/Users/`、主机名、局域网地址。 |
| 4.3 | 不写历史经过：「原先……现在改成……」「曾经」「一度」。历史在 git 里。如果那段历史仍在约束读者，就写成规矩（「不要再调用自探测」），不写成故事。 |
| 4.4 | 不写自我检讨。只写这次改了什么、依据是什么。 |
| 4.5 | 改自己的错时，不点名牵涉到的人，用中性措辞。 |
| 4.6 | 不评价其他移植项目，不记录外部传闻。 |
| 4.7 | 不写设备标识和私密数据：IMEI、ICCID、EID、序列号、MAC 地址、网络名、校准数据。 |

### 5 各类文本的写法

| 文本 | 写法 |
|---|---|
| README | 只写读者能据此判断的内容：能跑到哪一步、哪些硬件可用、怎么构建和写入、证据在哪。原理写进 `docs/`。 |
| 给机主的报告 | 先结论，再依据，最后写需要机主做的事或决定。需要机主决定时，只问一件事，给出选项。 |
| 派活消息 | 写现状、要做的事、规矩、交付什么。要做的事按步骤编号。 |
| 交活消息 | 写改了什么、跑过哪些检查、上机看点、没做和不确定的部分。 |
| 上机看点 | 每个看点写日志行原文或界面上能看到的现象，不写「工作正常」。 |

## 定词

下面每组词在本仓库里容易轮换。每组只选一个，一篇文本里不换。

- 校验、核对、检查、验证
- 删除、移除、剔除
- 报错、错误、异常、失败。报错指出现的提示，失败指操作没成功。
- 运行、执行、跑
- 显示、展示、呈现
- 编、编译、构建
- 上机、真机、实机。上机指在 Coachz 上启动这张镜像。
- 镜像、image
- 日志环、log ring、磁盘日志

## 空话替换表

| 写了 | 改成 |
|---|---|
| 值得注意的是、需要指出的是、重要的是 | 删掉，直接写事实 |
| 进行修改、进行校验 | 修改、校验 |
| 对 X 进行了 Y | Y 了 X |
| 实现了对 X 的支持 | 支持 X |
| 有效地、显著地、极大地、全面地 | 删掉，或给出数字 |
| 无缝、一站式、强大的、完善的、健壮的 | 删掉，或写出可测量的性质 |
| 旨在、致力于、用于实现 | 删掉，直接写它做什么 |
| 基于……的考虑、出于……的目的 | 因为、为了 |
| 在……的情况下 | 如果 |
| 一定程度上、某种意义上、相对而言 | 删掉，或给出范围 |
| 等等、之类、诸如此类 | 列全，或写「另外 N 项」 |
| 简单地、轻松地、只需 | 删掉 |
| 深入探讨、剖析 | 查看、分析 |
| 赋能、抓手、闭环、打通、链路 | 写具体动作 |
| 兜底、接住、收口、落盘 | 写具体动作：保底处理、处理、结束、写入磁盘 |
| 不仅……而且……、不是……而是……（修辞对仗） | 只写事实那一半 |
| 综上所述、总而言之、总的来说 | 删掉 |
| 我们可以看到、可以发现、让我们 | 删掉 |

## 不动的内容

以下内容原样保留，不套用本规范：

- 代码块、行内代码、标识符、命令、参数、文件路径
- 报错原文、日志行、反汇编
- iPadOS 界面上显示的文字
- 启动参数、/chosen 属性名、寄存器名、版本号

## 自检

交付前对草稿跑完这五项。发现问题就改，改完再交付。

1. 数最长的三句。操作句超过 30 字、说明句超过 40 字，就拆开。
2. 搜「；」「进行」「值得注意」「旨在」「等等」「之类」「原先」「曾经」「兜底」「落盘」，每一处都按规则改掉。
3. 搜每个「如果」「当」「若」。条件要在动作前面。
4. 搜第 3 步没选中的同义词，换成选中的那个。
5. 改了 `README.md` 就跑禁词检查，命中就改写。

   ```bash
   grep -nE "用户|报告人|反馈者|提议者|他说|私下|本机|/Users/|IMEI|ICCID|EID|序列号" README.md
   ```

## 例子

改写前：

> 值得注意的是，本次更新对相机驱动进行了全面的优化，有效地解决了画面偏色等一系列问题，从而显著提升了使用体验。

改写后：

> 前摄画面按 GRBG 显影。OV5675 的缓冲区是 GRBG，按 BGGR 显影时红蓝取到绿色像素，画面发灰。

改动：

- 删掉「值得注意的是」「全面的」「有效地」「显著提升」。
- 「进行了优化」改成具体动作。
- 「等一系列问题」改成那一个具体问题。
- 一句拆成两句，每句一件事。
