# Trogdor-ipadOS

- Target: native iPadOS on HP Chromebook x2 11 / Google Coachz (SC7180).
- Read `docs/native-boot.md`, `docs/design.md`, and `docs/status.md` before changes.
- Preserve the factory Coreboot / TF-A / Depthcharge chain. The initial entry is a developer-mode signed FIT on removable media. A virtual machine is not the product target.
- Keep source observations, host verification, and hardware observations explicitly separate. Hardware attempts are recorded in `docs/hardware-tests.md`; the Linux log receiver has captured entry EL2, probe EL1, stage=3, and handoff EL2 directly on hardware; the source-XNU pre-MMU entry checkpoint has also executed at EL1, verified boot_args, and returned to Linux. That earlier checkpoint alone does not establish later initialization or a full kernel/OS boot.
- The separate MMU-on checkpoint has now passed on hardware: complete table-pool, EL1 register and AT translation checks succeeded before restoring state and returning to Linux. See `docs/xnu-mmu-checkpoint.md`. The later high-VA milestone is recorded separately; later platform/device initialization and a full XNU/iPadOS boot remain unverified; the bounded version6 platform/ADT milestone is recorded below.
- The high-VA/C-entry stack-read checkpoint has passed on hardware: original RET reached the real arm_init KVA, its original frame adjustment ran, diagnostic stack read and all register/table/AT checks passed, and Linux received the log. See `docs/xnu-highva-checkpoint.md`; this does not execute the C initialization body or validate stack writes.
- The version4 early-C checkpoint has passed on hardware: original arm_init stack saves, earliest C body, full boot_args copy and BootArgs store were validated after owned-arena cache maintenance, then Linux received all 15 required fields. It stops before cpu_data_init; the separate version5 milestone below covers the CPU data leaf, while the later version6 milestone below separately covers bounded platform initialization and ADT lookup. See docs/xnu-cinit-checkpoint.md.
- The version5 boot-CPU data checkpoint has passed on hardware: native SIMD/scalar stores, all CPU object bytes and guards, original register/frame/table/AT checks, and arena cache return passed; Linux received all 16 required fields. It stops before PE_init_platform and uses a diagnostic seed only for its bounded CPU object; remove that input before any later platform boot. The later version6 milestone covers bounded platform/ADT initialization; subsequent platform/interrupt/SMP initialization remains unverified. See docs/xnu-cpu-checkpoint.md.
- The version6 platform/ADT checkpoint has passed on hardware with all 19 required fields: normal zero CPU input, original platform state initialization, ADT binding and native arm-io lookup, full active-frame/global checks and Linux return. It stops before SoC property reads or MMIO; later platform/device initialization and a full OS boot remain unverified. See docs/xnu-platform-checkpoint.md.
- The version7 full pre-VM PE return checkpoint preserves the actual nonzero SoC ranges and normal CPU input, audits the whole PE_init_platform(FALSE) path, and stops before the timer helper. Host tests and review passed; the first attempt stayed black with no recovered log, so hardware execution is unverified. Its diagnostic control also stayed black without a recovered log; the cause remains unknown. Its diagnostic control preserves the full capture/table gates and may return failed data fields to Linux; this is not a successful checkpoint. Missing bus/CPU frequency properties produce zero fields and are a compatibility gap, not validated clock support. See docs/xnu-pe-checkpoint.md.
- The version8 SoC-property midpoint bisects the unverified PE path after native property reads/cache stores and before frame restore or later CPU/clock/model/debug work. The hardware attempt stayed black without a recovered log; a replay of the exact accepted mode6 payload with the current wrapper passed all 19 fields on hardware on 2026-10-30. This validates the common path at the old boundary only; added execution and mode-specific gates remain unverified. Host validation is separate from hardware acceptance; require 20 fields with `read_probe.py --xnu-soc`. See docs/xnu-soc-checkpoint.md.
- Do not assume Android ABL, a persistent splash framebuffer, EL1 entry, UFS storage, or an EFI interface.
- No automatic SPI, eMMC, partition, EC, or firmware writes. Image creation operates on ordinary files only.
- Do not publish firmware dumps, serials, calibration data, private guidance, Apple binaries, or root images.
- Keep upstream sources under ignored `upstream/`, pinned by `upstream.lock.json`. Preserve upstream licenses; do not copy large upstream trees into tracked source.
- Use `python3 tools/build.py` and `python3 -m unittest discover -s tests -v` for host verification. Never describe these checks as a real device boot.
