# XNU 同步异常与返回失败现场

mode6 的当前包装器回归对照已通过真机 19 字段；mode7／8 仍黑屏且无日志。现有完整现场／页表门限失败会在导出前停止，原生同步异常则进入尚未完成平台初始化的 XNU 异常处理器。继续仅移动停止点无法区分两种情况。

比较继续二分、接 AP UART 和增加受控诊断返回。选择诊断返回：复用已验证的 EL2 与 Linux 接收路径，既有成功条件保留；AP UART 仍可用于诊断通道本身失效时。不是完整内核异常恢复，也不从故障指令继续执行。

## 输入与同步异常

独立 version=9 以 mode8 的相同源内核、ADT、正常 CPU 输入和 SoC 属性停止点为基础。装载器将执行语义保持为 mode8，并单独记录诊断开关；旧八版本不启用该开关。固定审计原始 EL1 SP0／SP1 同步向量首条跳转和完整源内核，除原有停止点外，只把这两条跳转替换为专用 HVC。装载器在任何 arena 写入前复核诊断向量的对齐、文件后备、可执行属性和指令。异步异常及 EL2 自身异常仍停止，不会伪装为正常返回。

同步异常直接在向量第一条 HVC 到达 EL2，不运行原生异常处理器，不访问故障栈，不读取 FAR 指向的数据。EL2 保存 ESR_EL1、ELR_EL1、FAR_EL1、SPSR_EL1 和原有 27 项捕获字段；FAR 原样保留，其有效性按 ESR 判断。只有精确向量 HVC／预期检查点 HVC 可进入诊断传输门；重复或非预期入口停止。EL1 异常寄存器随原有翻译、栈和线程状态一起保存／恢复。

## 传输条件与成功条件

version=9 的失败传输门与成功验证分开：要求 EL2 来自精确检查点的 EL1t，或精确同步向量的 EL1h；MMU／缓存开启、TCR／TTBR／MAIR／VBAR 为预期值，参数与 HVC 的硬件 AT 结果正确，全部 64 KiB 表池逐字相等，自有 24 MiB arena 缓存清理完整。异常时的原始 SPSR 必须为 EL1t／EL1h，原始 ELR 必须对齐且落在固定审计的 18 段可执行前缀中；装载器复核这些范围均有可执行文件后备。完整表池只映射自有 arena；此前固定审计的执行路径也只向自有 arena 写入。EL2 栈、恢复快照、FDT、Linux 与 arena 不重叠。

传输门不要求故障位置的参数寄存器、FP 或活动帧符合正常检查点模型；这些值只作为失败现场。它不使用该现场提供的指针进行缓存范围选择、恢复或日志写入。清理范围和恢复地址均来自已固定的 EL2 符号和装载器元数据。页表／翻译／缓存或入口完整性未满足仍停止；MMU 开启前故障、无限循环和 panic 路径仍可能无日志。

严格成功仍要求原有全部捕获、AT、页表、CPU／PE／DT、SoC 缓存、活动帧和 guard。任何异常强制 checkpoint=0，既有成功读取器继续拒绝失败记录。诊断日志另含完整 27 字段、四项原始异常寄存器、独立捕获／表池结果和原因（0 成功、1 同步异常、2 捕获失败、3 普通数据失败）。专用诊断读取器验证容量、唯一性、传输门标记、字段一致性与失败标记，只报告诊断结果。

## 验证与设备准备

测试应覆盖正常／故障／捕获失败传输、每个安全门的拒绝、完整表池比较及已用／空项破坏、三处补丁及写入前输入拒绝、旧八版本兼容、诊断读取器缺失／重复／矛盾字段和实际交叉编译。实际指令主机对照核对原始正常路径与故障向量边界；主机不代替真机。独立设计／实现审查和最终产物校验后，才准备既有可清空外置介质，完整回读并保留手动启动。首次真机先验证诊断通道，结果与完整平台验收分开。独立 version=10 使用同样的诊断布局，在已通过的首次 ADT 查找边界额外单条 BRK；必须取得该精确位置与预期 BRK syndrome 的故障记录，才算异常通道对照通过。正常 HVC 不能代替此项，version=10 也不能作为 SoC 成功。

## 2026-10-30：包装器重定位缺陷与系统 CPU 模型

首次 version10 手动尝试仍持续黑屏，恢复内置 Linux 后没有 probe-log，异常通道未验收。补充完整系统模型后，原包装器在进入 XNU 前的 `xnu_pe_contract` 拒绝真实 ADT；mode6 绕过此函数，因此此前的 19 字段对照不能排除此缺陷。

独立检查原始对象与已发出的 ELF：`xnu_pe.c` 的属性白名单、子节点名和 DRAM 键字符串指针聚合产生 34 个已分配节 ABS64 重定位；`xnu_checkpoint.c` 的四个故障标签再产生 4 个。Image 链接到零，加载到非零物理地址后表内值仍是低地址，没有运行时修正。最终 ELF 的重定位已被链接器消耗，原有“无残留重定位”检查不能发现。此前本机 `-shared -fPIC` 测试由动态加载器修正指针，因此漏检。这是确定的生成码缺陷，足以解释早于 XNU 入口的失败；无真机早期日志仍不能证明每轮黑屏的具体停止位置。

修复只把四处聚合改为内联字符数组，保留相同字符串、属性许可和严格返回门。新增 `relocation_audit.py` 在最终链接前审计实际 C 源文件的 AArch64 对象，拒绝加载节的绝对符号地址，并将逐文件结果写入构建清单；旧指针表夹具必须失败，内联数组／PC 相对引用／固定数字 KVA 必须通过。118 项主机回归与四种探针构建通过，修复后对象不存在上述重定位。

`qemu_probe.py` 使用 QEMU 11.1.3 TCG 的完整 CPU／异常级模型运行真实包装器和未改动源码负载。mode6 通过严格 19 字段；version9 的正常 SoC 路径通过全部 20 字段且 reason=0、checkpoint=1；version10 实际 BRK 后经 EL1 同步向量 HVC 返回 EL2，精确 ESR／ELR、完整表池与诊断传输门通过，reason=1、checkpoint=0。version10 在两个非零、2 MiB 对齐加载位置均通过。独立审查重新核对四次结果。

该工具的板级 FDT 准入、日志导出和 Linux 入口使用桩，不模拟 SC7180 外设，也不验证真实 Linux 启动或物理缓存一致性。它验证模型中的 MMU／异常分派／恢复指令，不算硬件通道通过。哈希命名的内嵌负载和链接后逐字节核对避免汇编 `.incbin` 缓存混用；version9 必须额外通过严格 SoC 读取器，不能把失败传输当作正常回归。使用已安装的 QEMU 和既有负载，例如：

```sh
python3 tools/qemu_probe.py --qemu path/to/qemu-system-aarch64 \
  --payload build/xnu-fault-control-first/payload.bin --output build/qemu-fault-check
```

普通测试不自动安装 QEMU。真实目标仍为原厂启动链上的原生执行；修复后的同一 version10 BRK 负载应重新验收，随后再运行 version9 定位后续路径。
